AI模型部署实战：从模型文件到高并发API

CaesarTools 技术文章 · 2026-10-15 📅 2026-10-15

一、模型部署到底在做什么

数据科学家在Jupyter里把模型训练好，得到一个model.pth文件。但这只是文件，用户没法直接用。部署就是把这个文件包装成一个API服务：发一张图片过来，模型返回识别结果；发一段文字，模型返回生成内容。和普通后端服务的区别是：推理要吃GPU显存，延迟敏感，流量忽高忽低。

二、基础方案：FastAPI加Transformers

from fastapi import FastAPI

from pydantic import BaseModel

import torch

from transformers import AutoModelForCausalLM, AutoTokenizer

app = FastAPI()

model = AutoModelForCausalLM.from_pretrained("Qwen/Qwen2-1.5B")

tokenizer = AutoTokenizer.from_pretrained("Qwen/Qwen2-1.5B")

class Prompt(BaseModel):

text: str

@app.post("/generate")

def generate(prompt: Prompt):

inputs = tokenizer(prompt.text, return_tensors="pt")

outputs = model.generate(**inputs, max_new_tokens=100)

return {"result": tokenizer.decode(outputs[0])}

启动：uvicorn main:app --port 8000。简单但并发低，一个请求推理时其他请求排队。

三、高并发方案：vLLM

7B以上模型，原生transformers每秒只能处理几个请求。vLLM用PagedAttention技术，把显存利用率从20%提到90%，吞吐量提升10到20倍。

pip install vllm

python -m vllm.entrypoints.openai.api_server --model Qwen/Qwen2-7B

直接暴露OpenAI兼容接口，前端代码改个base_url就能用，不用改业务代码。

四、量化：让模型在消费级GPU跑起来

7B模型FP16要14GB显存。量化到INT4只要4GB，一张RTX 4090就能跑。

from transformers import BitsAndBytesConfig

quant_config = BitsAndBytesConfig(load_in_4bit=True)

model = AutoModelForCausalLM.from_pretrained("Qwen/Qwen2-7B", quantization_config=quant_config)

代价是精度略降，但对大多数场景无感。

五、GPU选择参考

7B INT4：RTX 4090 24GB够。

7B FP16：A10G 24GB。

70B INT4：A100 80GB。

70B FP16：多卡A100。

云厂商按小时租：AutoDL、阿里云、AWS。测试用4090，生产用A10。

六、常见坑

模型加载慢，第一次加载几十亿参数要1到2分钟，启动后预热一个请求。显存OOM，长文本加大batch直接爆，限制max_tokens开vLLM连续批处理。并发低，原生transformers一次一个请求，用vLLM。同步阻塞，用FastAPI异步不要Flask。

七、和业务后端怎么配合

AI服务独立部署在GPU机器，业务后端通过HTTP调AI服务。不要把AI模型塞进业务后端进程，抢CPU还不好扩容。

八、监控

GPU利用率、显存占用、推理延迟P99、QPS。用Prometheus加Grafana。GPU利用率长期低于30%就是浪费钱，高于90%就要加卡。

九、模型版本管理

训练好几个版本模型，用环境变量MODEL_VERSION切换权重文件。A/B测试同时跑两个版本，按流量比例分流。

十、总结

模型部署不是把模型跑起来就完了。选对框架vLLM、做量化压显存、控制并发和延迟、GPU监控成本，这一整套才是生产级AI部署。个人开发者一张4090就能跑7B模型，企业级用A100集群跑70B。
