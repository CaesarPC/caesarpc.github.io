Git实战：从分支管理到代码Review

CaesarTools 技术文章 · 2026-10-15

一、Git为什么是标配

多人协作没有版本控制就是灾难。Git是分布式版本系统，每台电脑有完整历史，离线也能提交。GitHub/GitLab是远程仓库。

二、分支工作流

main分支永远可部署。新功能开feature分支：

git checkout -b feature/login

开发完发Pull Request，同事Review，合并到main。

不要直接在main上改。

三、提交信息规范

feat: 新功能

fix: 修bug

docs: 文档

refactor: 重构

test: 测试

写清楚做了什么，不要写"更新"。半年后没人知道改了啥。

四、冲突解决

两人改同一行：

<<<<<<< HEAD

你的

=======

别人的

>>>>>>> branch

手动保留正确部分，删掉标记，git add再commit。

预防：小步提交、经常pull、分支别活太久。

五、撤销操作

git checkout -- file 撤销未暂存修改

git reset HEAD file 取消暂存

git revert abc123 安全撤销提交

git reset --hard abc123 强制回退（危险）

六、暂存

git stash把未提交改动收起来，切分支干别的，回来git stash pop恢复。

七、.gitignore

node_modules、.env、dist、.DS_Store不要提交。

八、大文件

视频、模型权重不要直接git add。用Git LFS或者对象存储。仓库越搞越大，clone要半小时。

九、密钥泄露

API Key提交到公开仓库，立刻删、换密钥、改历史。GitHub会自动扫到常见密钥格式。

十、代码Review

PR不是走形式。看逻辑、看测试、看命名。被Review不要觉得被针对，是互相提高。

十一、回滚生产

git revert上个坏提交，push，自动重新部署。不要force push共享分支。

十二、变基vs合并

main更新了，feature分支同步：

git merge main：产生合并提交，历史分叉。

git rebase main：把提交挪到main最新后，历史直线。

rebase历史干净，但不要在共享分支上rebase。

十三、总结

Git是工程师基本功。分支工作流、规范提交、冲突解决、.gitignore、PR Review。工具简单，难的是养成习惯。
