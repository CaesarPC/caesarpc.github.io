RESTful API设计规范实战（2）

CaesarTools 技术文章 · 2026-10-15

一、API为什么需要规范

前后端协作最怕接口不统一。今天GET /getUserList，明天POST /user/query，后天/user_list。前端每个接口都要问后端。RESTful就是一套约定，让任何人看URL就知道这个接口干嘛。

二、URL用名词不用动词

正确：GET /users、POST /users、GET /users/123、PUT /users/123、DELETE /users/123。

错误：GET /getUserList、POST /deleteUser。

用HTTP方法表达操作，URL只表示资源。

三、HTTP方法语义

GET查询，幂等无副作用。POST创建。PUT全量更新。PATCH部分更新。DELETE删除。

不要所有操作都用POST。查询用GET才能被CDN缓存。

四、状态码

200成功。201创建成功。204无内容（DELETE成功）。400参数错。401未登录。403无权限。404不存在。429限流。500服务器错。

不要所有错误都返回200。前端要靠状态码判断处理。

五、统一响应格式

成功：

{ "code": 0, "data": {...}, "message": "ok" }

错误：

{ "code": 40001, "message": "邮箱已存在", "field": "email" }

field字段让前端把错误信息直接显示在对应输入框下面。不要只返回"参数错误"，前端不知道哪个字段错。

六、分页和过滤

GET /users?page=1&limit=20

返回带总数：{ "data": [...], "total": 100, "page": 1 }

过滤：GET /users?role=admin

排序：GET /users?sort=-created_at（负号倒序）

七、版本管理

/api/v1/users、/api/v2/users。老客户端继续用v1，新客户端用v2。不要直接改v1破坏老客户端。

八、认证

Authorization: Bearer eyJhbGciOi...

不要把token放URL query里，会被日志记录。

九、常见反模式

坑1：URL里写动词。

坑2：POST承担所有操作。查询也用POST。

坑3：返回HTML错误页。API必须返回JSON。

坑4：字段命名不统一。一会儿user_name一会儿username。统一snake_case。

十、限流

接口要限流防刷。同IP每分钟100次，超过返回429 Too Many Requests。登录接口失败5次锁账号10分钟。

十一、文档

用OpenAPI（Swagger）自动生成文档。改代码自动更新文档。前端不用问后端，打开文档自己看。

十二、总结

RESTful核心思想：资源用名词URL、操作用HTTP方法、状态码真实、格式统一。按这套规范写，前后端协作效率翻倍，新接手的人看URL就知道接口干嘛。
