RESTful API设计实战：从URL到错误处理

CaesarTools 技术文章 · 2026-10-15 📅 2026-10-15

一、API为什么需要规范

前后端协作最怕接口不统一。今天GET /getUserList，明天POST /user/query，后天/user_list。前端每个接口都要问后端。RESTful就是一套约定，让任何人看URL就知道接口干嘛。

二、URL设计

URL是名词，不是动词。

正确：GET /users、POST /users、GET /users/123、PUT /users/123、DELETE /users/123。

错误：GET /getUserList、POST /deleteUser。

用HTTP方法表达操作，URL只表示资源。

三、HTTP方法语义

GET查询，幂等无副作用。POST创建。PUT全量更新。PATCH部分更新。DELETE删除。

不要所有操作都用POST。查询用GET才能被CDN缓存。

四、状态码

200成功。201创建成功。204无内容（DELETE成功）。400参数错。401未登录。403无权限。404不存在。429限流。500服务器错。

不要所有错误都返回200。前端要靠状态码判断处理。

五、统一响应格式

成功：

{ "code": 0, "data": {...}, "message": "ok" }

错误：

{ "code": 40001, "message": "邮箱已存在", "field": "email" }

field字段让前端把错误显示在对应输入框下面。

六、分页

GET /users?page=1&limit=20

返回带总数：

{ "data": [...], "total": 100, "page": 1 }

七、过滤排序

GET /users?role=admin&sort=-created_at

负号表示倒序。

八、版本管理

/api/v1/users、/api/v2/users。

老客户端继续用v1，新客户端用v2。不要直接改v1破坏老客户端。

九、认证

Authorization: Bearer eyJhbGciOi...

不要把token放URL query（会被日志记录）。

十、常见反模式

坑1：URL里写动词。

坑2：POST做查询。

坑3：返回HTML错误页。

坑4：字段命名混乱（user_name和username混用）。

十一、文档

用OpenAPI/Swagger自动生成文档。改代码自动更新。前端不用问后端。

十二、限流和版本

接口要限流，防刷。同一个IP每分钟100次。超过返回429。版本号放URL或者Header，不要直接改老接口。

十三、总结

RESTful核心：名词URL、HTTP方法、真实状态码、统一格式。按这套来，前后端协作效率翻倍。
