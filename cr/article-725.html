Git团队协作规范（3）

CaesarTools 技术文章 · 2026-10-15

一、Git为什么是标配

多人协作没有版本控制就是灾难。你覆盖我的改动，我删你的文件，改坏了找不回。Git是分布式版本控制系统，每台电脑有完整历史，离线也能提交。GitHub和GitLab是远程仓库托管平台。

二、分支工作流

main分支永远可部署。新功能开feature分支：git checkout -b feature/user-login。开发完发Pull Request，同事Review代码后合并到main。不要直接在main上改。

三、提交信息规范

feat: 新功能

fix: 修bug

docs: 文档

refactor: 重构

test: 测试

写清楚做了什么，不要写"更新"。半年后没人知道改了啥。

四、冲突解决

两个人改了同一行代码，git merge冲突：

<<<<<<< HEAD

你的改动

=======

别人的改动

>>>>>>> branch-name

手动保留正确的部分，删掉标记，git add再commit。预防方法：小步提交、经常pull、分支别活太久。

五、撤销操作

git checkout -- file 撤销未暂存的修改

git reset HEAD file 取消暂存

git revert abc123 安全撤销某个提交

git reset --hard abc123 强制回退（危险，别在共享分支用）

六、暂存

git stash把未提交改动收起来，切分支干别的，回来git stash pop恢复。

七、.gitignore

node_modules、.env、dist、.DS_Store不要提交。

八、大文件

视频、模型权重不要直接git add，仓库越搞越大，clone要半小时。用Git LFS或者对象存储。

九、密钥泄露

API Key提交到公开仓库，立刻删、换密钥、改历史。GitHub会自动扫到常见密钥格式。

十、代码Review

PR不是走形式。看逻辑对不对、有没有测试、命名清不清楚。被Review不要觉得被针对，是互相提高。

十一、回滚生产

git revert上个坏提交，push，自动重新部署回滚。不要force push共享分支。

十二、变基vs合并

main更新了，feature分支同步：merge产生合并提交，历史分叉。rebase把提交挪到main最新后，历史直线。rebase历史干净，但不要在共享分支用。

十三、GitHub Flow

小团队推荐简化流程：main永远可部署，新功能开feature分支，开发完发PR，Review通过合并main，main自动部署。hotfix直接在main上修。大项目用Git Flow：develop开发分支、release预发布分支、hotfix修复分支。

十四、总结

Git是工程师基本功。分支工作流、规范提交信息、冲突解决、.gitignore、PR Review。工具简单，难的是养成规范习惯。团队协作Git用得好，效率翻倍。
