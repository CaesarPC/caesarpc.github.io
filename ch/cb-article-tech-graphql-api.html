GraphQL API設計：讓前端按需取數的新範式

RESTful API有個經典痛點：後端返回的數據要麼太多（列表接口帶了一堆前端不用的字段），要麼太少（還要再發一個請求獲取詳情）。前端要反覆找後端加字段、改接口。GraphQL是Facebook提出的API查詢語言，解決這個問題：前端精確聲明需要哪些數據，後端按聲明返回。

GraphQL的核心是類型系統。後端定義一張Schema：有哪些類型、每個類型有哪些字段、字段之間什麼關係。前端寫一個查詢（Query），描述自己需要哪些字段，後端執行查詢，返回的JSON結構和查詢結構完全一致。

舉個例子：REST要拿用戶信息和他的最新文章，可能要調/user/123和/user/123/posts兩個接口。GraphQL一個查詢搞定：query { user(id: 123) { name avatar posts(first: 5) { title date } } }。後端知道你要name、avatar，以及5篇文章的title和date，一次返回。

GraphQL的優勢：按需取數（不多不少）、強類型（Schema就是文檔）、內省（工具自動生成API文檔）、前端靈活（不用等後端改接口）。這些特點在多端、複雜數據關係的場景下特別有價值。

但GraphQL不是銀彈。它的缺點：學習曲線（要學Schema定義、Resolver、查詢語法）；緩存複雜（REST用URL做緩存鍵很自然，GraphQL所有請求都打到同一個URL，緩存需要專門處理）；性能風險（前端可以寫很深的嵌套查詢，一次請求打爆後端，需要限制查詢深度和複雜度）；文件上傳、實時訂閱（Subscriptions）比REST麻煩。

實際使用建議：複雜的、數據關係多的BFF層用GraphQL很合適；簡單的CRUD接口用REST更直接。不要全棧Graph化，選擇適合的場景。

Apollo是最流行的GraphQL框架，前後端都有成熟庫。後端用Apollo Server定義Schema和Resolver，前端用Apollo Client發查詢、做緩存、管理加載狀態。工具鏈完善，開發體驗好。

REST和GraphQL不是替代關係，而是互補。很多公司的做法是：內部微服務之間用REST/gRPC，對外的BFF層用GraphQL服務前端。各取所長。
