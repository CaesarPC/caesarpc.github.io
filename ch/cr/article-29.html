RESTful API設計實戰：從URL到錯誤處理

CaesarTools 技術文章 · 2026-10-15

一、API為什麼需要規範

前後端協作最怕接口不統一。今天GET /getUserList，明天POST /user/query，後天/user_list。前端每個接口都要問後端。RESTful就是一套約定，讓任何人看URL就知道接口乾嘛。

二、URL設計

URL是名詞，不是動詞。

正確：GET /users、POST /users、GET /users/123、PUT /users/123、DELETE /users/123。

錯誤：GET /getUserList、POST /deleteUser。

用HTTP方法表達操作，URL只表示資源。

三、HTTP方法語義

GET查詢，冪等無副作用。POST創建。PUT全量更新。PATCH部分更新。DELETE刪除。

不要所有操作都用POST。查詢用GET才能被CDN緩存。

四、狀態碼

200成功。201創建成功。204無內容（DELETE成功）。400參數錯。401未登錄。403無權限。404不存在。429限流。500服務器錯。

不要所有錯誤都返回200。前端要靠狀態碼判斷處理。

五、統一響應格式

成功：

{ "code": 0, "data": {...}, "message": "ok" }

錯誤：

{ "code": 40001, "message": "郵箱已存在", "field": "email" }

field字段讓前端把錯誤顯示在對應輸入框下面。

六、分頁

GET /users?page=1&limit=20

返回帶總數：

{ "data": [...], "total": 100, "page": 1 }

七、過濾排序

GET /users?role=admin&sort=-created_at

負號表示倒序。

八、版本管理

/api/v1/users、/api/v2/users。

老客戶端繼續用v1，新客戶端用v2。不要直接改v1破壞老客戶端。

九、認證

Authorization: Bearer eyJhbGciOi...

不要把token放URL query（會被日誌記錄）。

十、常見反模式

坑1：URL裡寫動詞。

坑2：POST做查詢。

坑3：返回HTML錯誤頁。

坑4：字段命名混亂（user_name和username混用）。

十一、文檔

用OpenAPI/Swagger自動生成文檔。改代碼自動更新。前端不用問後端。

十二、限流和版本

接口要限流，防刷。同一個IP每分鐘100次。超過返回429。版本號放URL或者Header，不要直接改老接口。

十三、總結

RESTful核心：名詞URL、HTTP方法、真實狀態碼、統一格式。按這套來，前後端協作效率翻倍。
