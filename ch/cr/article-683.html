Git團隊協作規範（2）

CaesarTools 技術文章 · 2026-10-15

一、Git為什麼是標配

多人協作沒有版本控制就是災難。你覆蓋我的改動，我刪你的文件，改壞了找不回。Git是分佈式版本控制系統，每臺電腦有完整歷史，離線也能提交。GitHub和GitLab是遠程倉庫託管平臺。

二、分支工作流

main分支永遠可部署。新功能開feature分支：git checkout -b feature/user-login。開發完發Pull Request，同事Review代碼後合併到main。不要直接在main上改。

三、提交信息規範

feat: 新功能

fix: 修bug

docs: 文檔

refactor: 重構

test: 測試

寫清楚做了什麼，不要寫"更新"。半年後沒人知道改了啥。

四、衝突解決

兩個人改了同一行代碼，git merge衝突：

<<<<<<< HEAD

你的改動

=======

別人的改動

>>>>>>> branch-name

手動保留正確的部分，刪掉標記，git add再commit。預防方法：小步提交、經常pull、分支別活太久。

五、撤銷操作

git checkout -- file 撤銷未暫存的修改

git reset HEAD file 取消暫存

git revert abc123 安全撤銷某個提交

git reset --hard abc123 強制回退（危險，別在共享分支用）

六、暫存

git stash把未提交改動收起來，切分支幹別的，回來git stash pop恢復。

七、.gitignore

node_modules、.env、dist、.DS_Store不要提交。

八、大文件

視頻、模型權重不要直接git add，倉庫越搞越大，clone要半小時。用Git LFS或者對象存儲。

九、密鑰泄露

API Key提交到公開倉庫，立刻刪、換密鑰、改歷史。GitHub會自動掃到常見密鑰格式。

十、代碼Review

PR不是走形式。看邏輯對不對、有沒有測試、命名清不清楚。被Review不要覺得被針對，是互相提高。

十一、回滾生產

git revert上個壞提交，push，自動重新部署回滾。不要force push共享分支。

十二、變基vs合併

main更新了，feature分支同步：merge產生合併提交，歷史分叉。rebase把提交挪到main最新後，歷史直線。rebase歷史乾淨，但不要在共享分支用。

十三、GitHub Flow

小團隊推薦簡化流程：main永遠可部署，新功能開feature分支，開發完發PR，Review通過合併main，main自動部署。hotfix直接在main上修。大項目用Git Flow：develop開發分支、release預發佈分支、hotfix修復分支。

十四、總結

Git是工程師基本功。分支工作流、規範提交信息、衝突解決、.gitignore、PR Review。工具簡單，難的是養成規範習慣。
