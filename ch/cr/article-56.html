前端狀態管理：從useState到Redux/Zustand

CaesarTools 技術文章 · 2026-10-15

一、狀態為什麼會亂

組件多了，狀態到處放。A組件的狀態B組件要用，C組件改了D組件不知道。prop一層層傳（prop drilling），代碼又臭又長。

狀態管理庫就是把共享狀態提到外面，任何組件直接讀寫。

二、React內置方案

useState管組件本地狀態。useContext跨層級傳狀態。

簡單場景夠用。複雜場景要外部庫。

三、Redux

單向數據流：action→reducer→state→view。可預測，好調試。Redux DevTools時光旅行。

但樣板代碼多，新手勸退。現代Redux Toolkit簡化了。

四、Zustand

極簡：const useStore = create((set) => ({ count: 0, inc: () => set(s => ({count: s.count+1})) }))。組件直接useStore()。

API簡單，體積小，2024年新項目推薦。

五、TanStack Query

服務器狀態單獨管。緩存、後台刷新、失敗重試。不要把服務器數據塞Redux。

useQuery({ queryKey:['users'], queryFn:fetchUsers })。自動緩存，第二次讀秒開。

六、什麼時候用什麼

- 組件本地狀態：useState

- 跨層級主題/用戶：useContext

- 複雜客戶端狀態：Zustand

- 服務器數據：TanStack Query

- 大型企業項目：Redux Toolkit

七、常見坑

坑1：所有狀態塞一個store。拆成多個store。

坑2：服務器數據塞客戶端store。用TanStack Query。

坑3：狀態更新不規範。直接改state，視圖不更新。

坑4：過度使用。小項目不需要狀態庫。

八、狀態和請求的關係

客戶端狀態（UI開關、表單草稿）和服務器狀態（用戶數據、列表）要分開管。TanStack Query管服務器狀態，Zustand管客戶端狀態。混在一起調試噩夢。

九、總結

狀態管理按場景選。本地用useState，跨層級用Context，複雜客戶端用Zustand，服務器數據用TanStack Query。不要為了用庫而用庫。
