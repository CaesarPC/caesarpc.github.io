AI模型部署實戰：從模型文件到高併發API（2）

CaesarTools 技術文章 · 2026-10-15

一、模型部署到底在做什麼

數據科學家在Jupyter裡把模型訓練好，得到一個model.pth文件。但這只是文件，用戶沒法直接用。部署就是把這個文件包裝成一個API服務：發一張圖片過來，模型返回識別結果；發一段文字，模型返回生成內容。和普通後端服務的區別是：推理要喫GPU顯存，延遲敏感，流量忽高忽低。

二、基礎方案：FastAPI加Transformers

from fastapi import FastAPI

from pydantic import BaseModel

import torch

from transformers import AutoModelForCausalLM, AutoTokenizer

app = FastAPI()

model = AutoModelForCausalLM.from_pretrained("Qwen/Qwen2-1.5B")

tokenizer = AutoTokenizer.from_pretrained("Qwen/Qwen2-1.5B")

class Prompt(BaseModel):

text: str

@app.post("/generate")

def generate(prompt: Prompt):

inputs = tokenizer(prompt.text, return_tensors="pt")

outputs = model.generate(**inputs, max_new_tokens=100)

return {"result": tokenizer.decode(outputs[0])}

啟動：uvicorn main:app --port 8000。簡單但併發低，一個請求推理時其他請求排隊。

三、高併發方案：vLLM

7B以上模型，原生transformers每秒只能處理幾個請求。vLLM用PagedAttention技術，把顯存利用率從20%提到90%，吞吐量提升10到20倍。

pip install vllm

python -m vllm.entrypoints.openai.api_server --model Qwen/Qwen2-7B

直接暴露OpenAI兼容接口，前端代碼改個base_url就能用，不用改業務代碼。

四、量化：讓模型在消費級GPU跑起來

7B模型FP16要14GB顯存。量化到INT4只要4GB，一張RTX 4090就能跑。

from transformers import BitsAndBytesConfig

quant_config = BitsAndBytesConfig(load_in_4bit=True)

model = AutoModelForCausalLM.from_pretrained("Qwen/Qwen2-7B", quantization_config=quant_config)

代價是精度略降，但對大多數場景無感。

五、GPU選擇參考

7B INT4：RTX 4090 24GB夠。

7B FP16：A10G 24GB。

70B INT4：A100 80GB。

70B FP16：多卡A100。

雲廠商按小時租：AutoDL、阿里雲、AWS。測試用4090，生產用A10。

六、常見坑

模型加載慢，第一次加載幾十億參數要1到2分鐘，啟動後預熱一個請求。顯存OOM，長文本加大batch直接爆，限制max_tokens開vLLM連續批處理。併發低，原生transformers一次一個請求，用vLLM。同步阻塞，用FastAPI異步不要Flask。

七、和業務後端怎麼配合

AI服務獨立部署在GPU機器，業務後端通過HTTP調AI服務。不要把AI模型塞進業務後端進程，搶CPU還不好擴容。

八、監控

GPU利用率、顯存佔用、推理延遲P99、QPS。用Prometheus加Grafana。GPU利用率長期低於30%就是浪費錢，高於90%就要加卡。

九、模型版本管理

訓練好幾個版本模型，用環境變量MODEL_VERSION切換權重文件。A/B測試同時跑兩個版本，按流量比例分流。

十、總結

模型部署不是把模型跑起來就完了。選對框架vLLM、做量化壓顯存、控制併發和延遲、GPU監控成本，這一整套才是生產級AI部署。個人開發者一張4090就能跑7B模型，企業級用A100集群跑70B。
