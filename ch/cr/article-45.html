AI推理服務部署：從模型加載到高併發API

CaesarTools 技術文章 · 2026-10-15

一、模型部署的挑戰

訓練好的模型是文件，用戶沒法直接用。部署就是把它包成API：發一張圖，返回識別結果；發一段文字，返回生成內容。和普通後端區別：推理喫GPU顯存，延遲敏感，流量忽高忽低。

二、基礎方案：FastAPI

from fastapi import FastAPI

from transformers import pipeline

app = FastAPI()

classifier = pipeline("sentiment-analysis")

@app.post("/predict")

def predict(text: str):

return classifier(text)[0]

uvicorn main:app --port 8000

簡單但併發低。一個請求推理時，其他請求排隊。

三、高併發：vLLM

7B以上模型，原生transformers每秒幾個請求。vLLM用PagedAttention，吞吐量提升10-20倍，顯存利用率從20%到90%。

python -m vllm.entrypoints.openai.api_server --model Qwen/Qwen2-7B

直接暴露OpenAI兼容接口，前端改個base_url就能用。

四、量化

7B FP16要14GB顯存。INT4量化只要4GB，一張4090就能跑。

BitsAndBytesConfig(load_in_4bit=True)。精度略降，多數場景無感。

五、GPU選擇

7B INT4：RTX 4090 24GB。

7B FP16：A10G 24GB。

70B INT4：A100 80GB。

雲租：AutoDL、阿里雲、AWS。測試用4090，生產用A10。

六、常見坑

坑1：模型加載慢。第一次加載幾十億參數要1-2分鐘。啟動後預熱一個請求。

坑2：顯存OOM。長文本+大batch爆。限制max_tokens，開vLLM連續批處理。

坑3：併發低。原生transformers一次一個請求。用vLLM。

坑4：同步阻塞。用FastAPI異步，不要Flask。

七、和業務後端配合

AI服務獨立部署在GPU機器，業務後端HTTP調AI服務。不要把模型塞進業務後端進程。

八、監控

GPU利用率、顯存、推理延遲P99、QPS。Prometheus+Grafana。GPU利用率長期低於30%就是浪費錢。

九、模型版本管理

訓練多個版本，用環境變量MODEL_VERSION切換權重文件。A/B測試同時跑兩個版本，按流量比例分流。

十、總結

AI部署：選vLLM高併發、量化壓顯存、獨立部署、監控GPU。個人一張4090跑7B，企業A100跑70B。
