API網關架構設計：微服務世界的統一入口

微服務拆成幾十個服務後，客戶端要直接調用幾十個服務嗎？手機APP要知道訂單服務地址、用戶服務地址、商品服務地址？後端服務地址變了、增加了新服務，APP都要發版更新？這顯然不現實。API網關就是解決這個問題的：所有客戶端請求統一經過網關，網關負責路由到對應的後端服務。

API網關是系統的統一入口。客戶端只需要知道網關的地址，不用關心後面有多少個服務。網關根據請求的路徑（如/order/*路由到訂單服務，/user/*路由到用戶服務）把請求轉發到對應的後端服務。這樣後端服務數量變化、地址變化，對客戶端完全透明。

網關承擔了很多橫切關注點（所有服務都需要但又不想每個服務都實現一遍的功能）：身份認證（驗證Token，通過後才轉發）、權限檢查、限流（防止某個客戶端刷爆）、日誌記錄（所有請求統一記錄）、監控統計（請求量、響應時間）、HTTPS終止（SSL證書在網關配置）。這些通用邏輯在網關統一做一次，後端服務只關注業務邏輯。

常見的API網關實現：Kong（開源，基於Nginx+Lua）、Spring Cloud Gateway（Java生態）、APISIX（開源，高性能）、雲廠商的託管API網關（阿里雲API網關、AWS API Gateway）。中小項目直接用雲廠商託管的，免運維；大型團隊可能自建開源網關。

除了基礎路由，網關還能做很多高級功能：請求轉換（把客戶端發的格式轉成後端需要的格式）、協議轉換（HTTP轉gRPC）、緩存（熱點請求在網關層緩存，不打到後端）、灰度發佈（按用戶ID把10%的請求路由到新版本服務）。BFF（Backend For Frontend）模式是網關的進階：為不同端（APP、Web、小程序）定製不同的聚合接口，在網關層聚合多個後端服務的數據，一次請求返回前端需要的全部數據，減少客戶端請求數。

網關也是安全防線。所有外部請求必須經過網關，後端服務不直接暴露公網。網關可以攔截惡意請求、SQL注入特徵、異常IP。沒有網關直接暴露後端服務，攻擊者可以隨意掃描探測。

高可用是網關必須考慮的。網關是所有流量的入口，如果網關掛了，整個系統就不可用了。網關必須集群部署，多實例負載均衡，任何一臺掛了其他頂上。網關自身的性能也要高：它要處理所有流量，不能成為瓶頸。

API網關是微服務架構的標配組件。理解它的定位和功能，才能設計出合理的微服務系統。沒有網關的微服務是一盤散沙，客戶端和服務之間的關係會亂成一團。
