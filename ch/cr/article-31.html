前端測試入門：單元測試、集成測試和E2E測試

CaesarTools 技術文章 · 2026-10-15

一、為什麼要寫測試

沒有測試的代碼，改一處不敢碰另一處。重構等於賭博。上線出bug只能靠用戶反饋。測試是給代碼上保險——改完跑一遍測試，知道沒破壞舊功能。

二、測試金字塔

底層：單元測試，多而快，測單個函數。

中層：集成測試，少而穩，測模塊間配合。

頂層：E2E測試，最少最慢，模擬用戶操作。

越往上越慢越貴。大部分測試應該是單元測試。

三、單元測試

測單個函數，不依賴外部。用Vitest（Vite原生）或Jest。

function add(a, b) { return a + b; }

test('1+1=2', () => {

expect(add(1,1)).toBe(2);

});

覆蓋正常情況、邊界情況、異常情況。

四、組件測試

React組件用Testing Library渲染組件，模擬點擊，斷言輸出。

import { render, screen, fireEvent } from '@testing-library/react';

test('點擊按鈕計數加一', () => {

render();

fireEvent.click(screen.getByText('+1'));

expect(screen.getByText('1')).toBeInTheDocument();

});

五、集成測試

測多個模塊配合。比如登錄流程：輸入賬號密碼→調API→跳首頁。API用MSW mock掉。

六、E2E測試

用Playwright或Cypress，真實瀏覽器模擬用戶操作。打開網站、點擊、輸入、斷言。慢但最接近真實。

七、覆蓋率

覆蓋率多少合適？80%是個參考線。不要為了覆蓋率寫無意義的測試。關鍵業務邏輯必須測。

八、CI裡跑測試

push代碼後GitHub Actions自動跑測試。掛了阻止合併。壞代碼上不了main。

九、常見誤區

坑1：不寫測試。遲早還債。

坑2：測試實現細節不測行為。重構測試就掛。

坑3：E2E測試寫太多。慢，維護成本高。

坑4：mock過度。什麼都mock等於沒測。

十、TDD測試驅動開發

先寫測試再寫代碼。測試定義行為，代碼讓測試通過。好處是代碼天然可測，設計更清晰。缺點是初期慢。

十一、總結

測試是工程成熟度標誌。單元測試主力，組件測試補充，E2E測關鍵流程。CI裡自動跑。寫測試不優雅，但省未來無數次救火。
