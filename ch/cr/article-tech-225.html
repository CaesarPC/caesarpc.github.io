# 冪等性設計：為什麼重複請求不能出問題

用戶點了"提交訂單"按鈕，網絡慢，他又點了一次。或者消息隊列重試了一次，同一個消息被消費了兩遍。如果不做冪等性處理，結果就是：用戶付了兩次錢、訂單創建了兩次、積分加了兩遍。冪等性是分佈式系統中必須考慮的問題——同一個操作執行一次和執行多次，結果應該一樣。

## 一、什麼是冪等

冪等（Idempotent）是一個數學概念：f(f(x)) = f(x)。在編程中，一個冪等操作執行一次和執行多次的效果相同。

HTTP方法的語義天然有區分：GET是冪等的（查多少次都一樣），POST不是冪等的（提交兩次創建兩條數據），PUT是冪等的（更新同一條記錄，執行多次結果一樣），DELETE是冪等的（刪兩次和刪一次效果一樣）。

但實際業務中，POST創建訂單、POST支付這種操作，如果用戶重複提交或者消息重複投遞，就會出問題。

## 二、怎麼實現冪等

最直接的方案：給每個請求一個唯一的請求ID。客戶端生成一個唯一ID（UUID或者雪花ID），和請求一起發給服務端。服務端先查這個ID有沒有處理過——處理過就直接返回上次的結果，不重複執行。

這個方案本質上是用一個唯一鍵做去重。數據庫裡建一張請求記錄表，請求ID做唯一索引。處理前先插入記錄，插入成功說明是第一次請求，執行業務；插入失敗說明是重複請求，直接返回。

## 三、天然冪等的操作

有些操作天然冪等，不需要額外處理： - 查詢操作：查多少次結果都一樣。 - 更新固定值：update set status = 1 where id = 123。執行多少次結果都是status=1。 - 刪除操作：delete from where id = 123。刪一次和刪十次，結果都是這條記錄沒了。

不冪等的操作： - 新增：insert into orders ...。執行兩次創建兩條訂單。 - 累加：update set balance = balance + 100。執行兩次加200，不對。

對於累加操作，改成set balance = balance + 100 where order_id = 'xxx' and processed = false——用條件控制，已經處理過的就不再累加。

## 四、消息隊列的冪等

前面說過消息隊列可能重複投遞。消費端必須做到冪等——同一個消息消費兩次，結果和消費一次一樣。

最常見的做法：消息帶一個唯一業務ID（比如訂單號），消費前先查這個ID是不是已經處理過了。處理過就跳過。數據庫唯一約束也能兜底——同一個訂單號的積分記錄唯一，重複插入會失敗。

## 五、總結

冪等性不是可選項，而是分佈式系統的必備設計。網絡會超時、用戶會重複點擊、消息會重複投遞——你無法保證操作只執行一次。但你可以保證執行多次結果和一次一樣，這就是冪等性的價值。
