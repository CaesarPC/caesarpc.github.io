RESTful API設計規範實戰（2）

CaesarTools 技術文章 · 2026-10-15

一、API為什麼需要規範

前後端協作最怕接口不統一。今天GET /getUserList，明天POST /user/query，後天/user_list。前端每個接口都要問後端。RESTful就是一套約定，讓任何人看URL就知道這個接口乾嘛。

二、URL用名詞不用動詞

正確：GET /users、POST /users、GET /users/123、PUT /users/123、DELETE /users/123。

錯誤：GET /getUserList、POST /deleteUser。

用HTTP方法表達操作，URL只表示資源。

三、HTTP方法語義

GET查詢，冪等無副作用。POST創建。PUT全量更新。PATCH部分更新。DELETE刪除。

不要所有操作都用POST。查詢用GET才能被CDN緩存。

四、狀態碼

200成功。201創建成功。204無內容（DELETE成功）。400參數錯。401未登錄。403無權限。404不存在。429限流。500服務器錯。

不要所有錯誤都返回200。前端要靠狀態碼判斷處理。

五、統一響應格式

成功：

{ "code": 0, "data": {...}, "message": "ok" }

錯誤：

{ "code": 40001, "message": "郵箱已存在", "field": "email" }

field字段讓前端把錯誤信息直接顯示在對應輸入框下面。不要只返回"參數錯誤"，前端不知道哪個字段錯。

六、分頁和過濾

GET /users?page=1&limit=20

返回帶總數：{ "data": [...], "total": 100, "page": 1 }

過濾：GET /users?role=admin

排序：GET /users?sort=-created_at（負號倒序）

七、版本管理

/api/v1/users、/api/v2/users。老客戶端繼續用v1，新客戶端用v2。不要直接改v1破壞老客戶端。

八、認證

Authorization: Bearer eyJhbGciOi...

不要把token放URL query裡，會被日誌記錄。

九、常見反模式

坑1：URL裡寫動詞。

坑2：POST承擔所有操作。查詢也用POST。

坑3：返回HTML錯誤頁。API必須返回JSON。

坑4：字段命名不統一。一會兒user_name一會兒username。統一snake_case。

十、限流

接口要限流防刷。同IP每分鐘100次，超過返回429 Too Many Requests。登錄接口失敗5次鎖賬號10分鐘。

十一、文檔

用OpenAPI（Swagger）自動生成文檔。改代碼自動更新文檔。前端不用問後端，打開文檔自己看。

十二、總結

RESTful核心思想：資源用名詞URL、操作用HTTP方法、狀態碼真實、格式統一。按這套規範寫，前後端協作效率翻倍，新接手的人看URL就知道接口乾嘛。
