AI推理服务部署：从模型加载到高并发API

CaesarTools 技術文章 · 2026-10-15

一、模型部署的挑战

训练好的模型是文件，用户没法直接用。部署就是把它包成API：发一张图，Back识别结果；发一段文字，Back生成内容。和普通后端区别：推理吃GPU显存，延迟敏感，流量忽高忽低。

二、基础方案：FastAPI

from fastapi import FastAPI

from transformers import pipeline

app = FastAPI()

classifier = pipeline("sentiment-analysis")

@app.post("/predict")

def predict(text: str):

return classifier(text)[0]

uvicorn main:app --port 8000

简单但并发低。一个请求推理时，其他请求排队。

三、高并发：vLLM

7B以上模型，原生transformers每秒几个请求。vLLM用PagedAttention，吞吐量提升10-20倍，显存利用率从20%到90%。

python -m vllm.entrypoints.openai.api_server --model Qwen/Qwen2-7B

直接暴露OpenAI兼容接口，前端改个base_url就能用。

四、量化

7B FP16要14GB显存。INT4量化只要4GB，一张4090就能跑。

BitsAndBytesConfig(load_in_4bit=True)。精度略降，多数场景无感。

五、GPU选择

7B INT4：RTX 4090 24GB。

7B FP16：A10G 24GB。

70B INT4：A100 80GB。

云租：AutoDL、阿里云、AWS。测试用4090，生产用A10。

六、常见坑

坑1：模型加载慢。第一次加载几十亿参数要1-2分钟。启动后预热一个请求。

坑2：显存OOM。长文本+大batch爆。限制max_tokens，开vLLM连续批处理。

坑3：并发低。原生transformers一次一个请求。用vLLM。

坑4：同步阻塞。用FastAPI异步，不要Flask。

七、和业务后端配合

AI服务独立部署在GPU机器，业务后端HTTP调AI服务。不要把模型塞进业务后端进程。

八、监控

GPU利用率、显存、推理延迟P99、QPS。Prometheus+Grafana。GPU利用率长期低于30%就是浪费钱。

九、模型版本管理

训练多个版本，用环境变量MODEL_VERSION切换权重文件。A/B测试同时跑两个版本，按流量比例分流。

十、总结

AI部署：选vLLM高并发、量化压显存、独立部署、监控GPU。个人一张4090跑7B，企业A100跑70B。
