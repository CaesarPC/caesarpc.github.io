# REST之外：GraphQL、gRPC與API設計的新選擇

RESTful API統治了Web世界十幾年，但它不是沒有缺點。前端經常抱怨：一個頁面要調三四個接口才能湊齊需要的數據；後端返回的字段太多，大部分用不上；要加一個字段還要後端改接口、發版，前端等着。這些痛點催生了新的API設計範式——GraphQL讓前端精確聲明需要什麼數據，gRPC讓服務間通信更快更高效。理解這些新範式的優缺點，知道什麼場景該用什麼，是現代後端開發者的必備知識。

## 一、REST的痛點：過度獲取與不足獲取

假設你在做一個用戶列表頁面，要顯示每個用戶的名字和最新一條動態。REST的做法是：先調 /api/users 拿到用戶列表，然後對每個用戶調一次 /api/users/{id}/posts 拿到最新動態。一頁20個用戶，就是21個請求——首屏加載慢得要命。

反過來的問題是過度獲取：你只是要顯示用戶名字，接口卻返回了用戶的郵箱、手機號、地址、訂單記錄一大堆字段。數據傳了一大堆，絕大部分沒用。

這些問題的根源是：REST接口的形狀是後端定義死的，前端只能被動接受。後端不知道前端需要什麼，前端沒法精確告訴後端。兩邊來回溝通改接口，效率很低。

## 二、GraphQL：前端說了算

GraphQL是Facebook開源的API查詢語言。它的核心思想是：前端不指定"訪問哪個URL拿什麼數據"，而是寫一個查詢，精確聲明自己需要哪些字段、嵌套關係是什麼。後端只暴露一個端點（通常是 /graphql），所有請求都發到這裡。

舉個例子，前端要查用戶的名字和最新動態的標題，就寫這樣的查詢： query { user(id: 123) { name posts(limit: 1) { title } } } 後端根據這個查詢，只返回 name 和 posts.title 這兩個字段，不多不少。

GraphQL的好處是顯而易見的。第一，按需取數：要什麼字段拿什麼字段，沒有多餘數據。第二，一個請求拿全嵌套數據：上面那個例子，一個查詢同時拿到用戶和他的動態，不用發多個請求。第三，前端迭代不用等後端改接口——要加字段就自己在查詢里加上，後端schema裡有的話直接就能用。

但GraphQL不是沒有代價。學習成本比REST高——你要學schema定義、resolver、查詢語法。緩存也更復雜：REST的URL天然就是緩存key，GraphQL所有請求都打到同一個URL，緩存策略要自己設計。N+1查詢問題也需要特別處理——如果不做優化，GraphQL可能會生成一堆低效的數據庫查詢。

GraphQL特別適合前端需求多變的場景：內容平臺、B端管理系統、移動端App。但簡單的CRUD接口，REST就夠了，沒必要上GraphQL。

## 三、gRPC：高性能的服務間通信

REST用JSON做數據格式，走HTTP，可讀性好但性能一般。gRPC是Google開源的高性能RPC框架，用Protocol Buffers做序列化，基於HTTP/2傳輸。

gRPC的工作方式是：你用.proto文件定義服務接口和數據結構，然後用工具自動生成各語言的客戶端和服務端代碼。調用遠端方法就像調用本地函數一樣簡單——不用手動拼接URL、不用手動序列化JSON。

gRPC的性能優勢主要來自Protocol Buffers。它是二進制格式，比JSON小得多、解析快得多。一個普通的JSON請求可能幾百字節，Protobuf可能只有幾十字節。在高併發服務間調用的場景下，這個差距累積起來非常可觀。

gRPC適合什麼場景？微服務之間的內部通信——服務A調用服務B，追求低延遲和高吞吐量。它不適合直接暴露給前端瀏覽器——瀏覽器不能直接發gRPC請求（需要gRPC-Web做轉換），而且二進制格式對人不友好，調試不方便。

所以常見的架構是：對外暴露REST或GraphQL API給前端，內部服務之間用gRPC通信。各取所長。

## 四、API設計的本質：不是風格之爭

REST、GraphQL、gRPC不是互相取代的關係，它們解決不同的問題。

REST簡單、通用、調試方便，適合對外的公開API。GraphQL靈活、按需取數，適合前端需求多變的B端和C端產品。gRPC高性能、強類型，適合內部微服務通信。

很多人糾結"我們應該用REST還是GraphQL"，好像選了一個就要拋棄另一個。實際上，一個成熟的系統往往是混合的：核心對外接口用REST保持簡單，複雜查詢場景用GraphQL，內部服務間用gRPC。選技術的時候不要原教旨主義，根據場景選最合適的。

## 五、API的未來：從手寫代碼到自動生成

無論用哪種風格，API設計的趨勢都是自動化。OpenAPI規範讓你用一份描述文件定義API，自動生成文檔、SDK、mock數據。GraphQL的schema自帶文檔和類型系統。gRPC的proto文件就是接口定義。

未來的開發者花在手寫API樣板代碼上的時間會越來越少。AI可以根據你的業務描述自動生成接口定義和CRUD代碼。但理解API設計的原則——一致性、可擴展性、安全性——這些不會因為工具自動化而過時。

## 六、總結

API設計是前後端協作的橋樑。這座橋設計得好，兩邊通行順暢；設計得差，天天堵車。REST是基礎，必須掌握；GraphQL和gRPC是進階工具，知道什麼時候用。不要被技術名詞嚇住，核心永遠是：你的調用方需要什麼，你怎麼最高效地把數據給他們。
