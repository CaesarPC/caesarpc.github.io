JavaScript異步編程深入：從回調地獄到Async/Await的進化之路

JavaScript是單線程語言，同一時間只能做一件事。如果做了一個耗時操作（髮網絡請求、讀文件、定時器），後面的代碼就得等着，頁面就卡死了。異步編程就是解決這個問題的機制：遇到耗時操作先掛起，繼續執行後面的代碼，等耗時操作完成後再回來處理結果。理解異步編程的演變過程，是掌握JavaScript核心的關鍵。

最早的異步方式是回調函數。比如setTimeout(fn, 1000)，1秒後執行fn；發請求時傳一個回調，服務器返回後自動調用。這種方式簡單直接，但嵌套多層之後就變成了"回調地獄"：回調裡面套回調，縮進四五層，代碼橫着走，根本沒法維護。比如要依次請求三個接口，就得寫成callback1(() => { callback2(() => { callback3(() => { ... }) }) })，可讀性極差。

Promise的出現解決了回調地獄。Promise是一個容器，包裹着一個異步操作的結果。它有三種狀態：pending（進行中）、fulfilled（成功）、rejected（失敗）。狀態一旦改變就不會再變。鏈式調用.then().then().then()讓異步操作可以像流水線一樣串聯，每層返回一個新的Promise，縮進整齊。錯誤用.catch統一捕獲，不像回調那樣每個回調都要處理錯誤。Promise是現代JavaScript異步的基礎，fetch、axios、動態import都是基於Promise。

但Promise鏈式調用寫多了還是有點囉嗦。Async/Await語法是Promise的語法糖，讓異步代碼看起來像同步代碼。async函數里可以用await等待一個Promise完成，代碼從上到下讀，和寫同步代碼一模一樣。try/catch捕獲錯誤也和同步代碼一致。這是目前異步編程的最佳寫法，新代碼應該全部用async/await。

事件循環（Event Loop）是理解JavaScript異步的底層機制。調用棧裡的代碼同步執行，遇到異步操作就交給瀏覽器/Node的API處理，註冊回調。同步代碼執行完後，事件循環從任務隊列裡取出異步任務的回調，放入調用棧執行。任務隊列又分宏任務（setTimeout、setInterval、I/O）和微任務（Promise.then、MutationObserver）。每次執行完一個宏任務，要清空所有微任務，然後才執行下一個宏任務。理解這個順序，才能搞懂為什麼setTimeout(fn, 0)比Promise.resolve().then(fn)後執行。

實際開發中的異步技巧包括：Promise.all()並行執行多個異步操作，等全部完成；Promise.race()取最快完成的那個；Promise.allSettled()等全部完成（不管成功失敗）。併發控制是常見需求：有100個請求要發，但同時發太多會把服務器打爆，需要限制併發數（比如同時最多5個）。寫一個簡單的併發控制器，或者用p-limit這類庫，就能解決。

錯誤處理是異步編程容易出錯的地方。async函數里await的Promise如果reject了，會拋出異常，必須用try/catch包裹，否則未捕獲的rejection會導致程序崩潰。並行請求時，Promise.all任何一個失敗就整體失敗，如果希望部分成功也算完成，要用Promise.allSettled。

常見的異步坑包括：for循環裡await（串行執行，很慢，應該用Promise.all並行）、忘記await（函數返回的是Promise而不是結果，後續代碼拿到的是Promise對象）、循環中動態await導致的執行順序問題。這些都是新手常犯的錯誤，理解了異步原理就能避免。

異步編程是JavaScript最核心的概念之一。從回調到Promise到Async/Await，語言一直在讓異步代碼寫得更像同步代碼。理解事件循環和微任務宏任務，才能寫出正確、高效、可維護的異步代碼。
